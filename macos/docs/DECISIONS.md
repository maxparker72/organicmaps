# Decisions

Each entry records a choice and why it was made. Add a new entry before reversing an old one, and mark the old one superseded. IDs are never reused. The project tracker mirrors this list.

## D-01 · Native SwiftUI app on the shared C++ engine
*Accepted · May 2026*

The Mac app is SwiftUI/AppKit in `macos/`, talking to the engine through the iOS `CoreApi` framework plus Mac-only `OM*` Objective-C++ bridges. It does not use the Qt desktop app in `qt/`.

**Why:** Qt is a developer tool upstream and doesn't feel like a Mac app. Reusing CoreApi gives iOS-tested wrappers for bookmarks, tracks and place pages.

## D-02 · The desktop app is a planner
*Accepted · May 2026*

Out of scope: turn-by-turn navigation, OSM editing, donate, auto-download, power saving, compass calibration (SPEC: RTE-07, SET-06).

**Why:** People plan trips at a desk and navigate with a phone. These features add cost without value on a Mac.

## D-03 · No perspective (3D tilt) view
*Accepted · May 2026*

Perspective is forced off. 3D buildings stay (SPEC: MAP-11).

**Why:** It adds nothing to planning, and the engine's desktop `Allow3dMode` branch needs two calls to toggle and still didn't flip reliably.

## D-04 · Xcode project generated by XcodeGen
*Accepted · May 2026*

`macos/project.yml` is the source of truth. `OMapsDesktop.xcodeproj` is generated and gitignored. Run `xcodegen generate` in `macos/` after adding files or changing the spec.

**Why:** Hand-edited pbxproj files conflict on every merge, and sources are picked up by directory.

## D-05 · Keep engine patches small and listed
*Accepted · Oct 2026*

Changes outside `macos/` are minimal and listed in ARCHITECTURE.md with their upstream status. Bug fixes that help upstream (for example the Metal drawable guard) are offered as upstream PRs.

**Why:** Every patch costs time on each upstream sync.

## D-06 · Tags and projects live in the KML data
*Accepted · May 2026*

Tags are stored in each item's KML properties (`tags`, `;`-separated). Projects are KML lists marked with a kind property.

**Why:** Tags and projects survive export, backup and re-import, and travel with the files.

## D-07 · Spec-driven development
*Accepted · Oct 2026*

Every feature has an ID in SPEC.md with an acceptance check. Tasks and commits reference IDs. A feature is marked Done only when its check passes on a Release build.

**Why:** The first sprint produced a lot of features quickly, but the parity matrix went stale on day one and the README claimed a feature that didn't exist.

## D-08 · One map engine for the life of the app, one main window
*Accepted · Oct 2026*

The drape engine and its Metal context factory belong to an app-lifetime owner, not to a SwiftUI view. The main scene is a single `Window`, not a `WindowGroup`.

**Why:** The engine assumes one instance per process. Owning it from a view caused a use-after-free when the window closed, and Cmd-N created a second engine.

## D-09 · Import never rewrites the user's styling
*Accepted · Oct 2026*

Imports keep the file's colors and line widths. Normalization is an explicit command (File menu). It isn't undoable yet; making it undoable is a follow-up.

**Why:** Automatic normalization forced every track to width 5 and snapped colors, which silently destroyed imported styling (SPEC: LIB-06).

## D-10 · Distribution through GitHub Releases with Developer ID signing
*Proposed · Oct 2026*

Tagged builds are produced by GitHub Actions: archive, sign with Developer ID, notarize, staple, package a DMG, publish a GitHub Release. In-app updates use Sparkle later.

**Why:** Testers get an app that opens without Gatekeeper warnings. **Open question:** this needs an Apple Developer Program membership ($99/year). Until then, builds are ad-hoc signed.

## D-11 · Follow upstream by merging, not rebasing
*Accepted · Nov 2026*

`macos-experiment` takes upstream with a merge commit (`[macos] Merge upstream master …`) on a `sync/upstream-<date>` branch, which is fast-forwarded once the app builds and launches. `git rerere` is on, so conflict resolutions are reused. Replaces the rebase plan in T-030.

**Why:** The branch is published, so rewriting it is unsafe. A merge resolves each conflict once instead of once per replayed commit, and the routine sync (`.claude/skills/macos-sync`) stays one repeatable procedure.

## D-12 · Bookmark colors follow upstream; the palette is display-only
*Accepted · Nov 2026*

Upstream stores a bookmark color as a preset `{X, 0}` or a custom `{None, rgba}` and normalizes on load. The Mac app reads the effective color, shows its true color in lists, and names the nearest of the 16 palette swatches. Writes go through `SetColor(dp::Color)`, like iOS. The editor writes the exact stored color back unless the user picked a different swatch (LIB-06). The Mac palette enum lives in `macos/MapView/OMBookmarkColor.h` (Swift `BookmarkColor`).

**Why:** Upstream (8aa1cd4d18) made the old `{palette, rgba}` pair invalid; keeping it would mean fighting the engine on every load. Full any-color editing is a separate feature.
