# Code review, October 2026

A read-through of `macos-experiment` at `70f6976` (30 May 2026). It covers the Objective-C++ bridges (`R-B`), the SwiftUI layer (`R-S`) and build, engineering and distribution (`R-E`).

**How these were found.** By reading the code. Nothing was found by running the app. Findings marked *confirmed* were re-checked against the source while this document was written. Findings marked *unverified* need a reproduction before they're fixed. The Debug build succeeds on Xcode 26.6, with 11 warnings in Mac code.

Each finding maps to a task in the tracker and, where it affects behaviour, to a feature row in SPEC.md.

## Summary

The bridge layer is thin and follows the iOS CoreApi patterns well: edit sessions, weak captures and main-thread delivery are mostly right. The serious problems fall into three groups.

1. **Lifecycle.** The engine, Metal context, listeners and storage subscriptions are tied to SwiftUI view lifetimes, but the engine expects one instance for the life of the process.
2. **Engine defaults the bridge didn't account for.** Route stops get reordered, ids 0 and `kInvalid*` both abort, colors live in two fields, and viewport search keeps running after it should stop.
3. **No single owner for library state.** Each model re-reads the engine through static calls. NotificationCenter is used to make up for missing change signals, and visibility is written from three places that don't know about each other.

Performance problems come from full-library and full-country-tree scans that run on every click, keystroke or progress update.

## Recommended refactors, in order

1. **One `LibraryStore`.** One owner for value-type rows (with tags, regions and visibility precomputed) that excludes project lists and hides `project:` tags. It rebuilds on one engine-changed signal. Tag, region and project indexes are derived from it. Addresses R-S2, R-S5, R-S13, R-S15 and R-B12.
2. **An engine protocol** injected into the models instead of static calls, with batch operations (one edit session) as the default. This makes models testable (R-E9).
3. **One visibility coordinator** with explicit normal, filtered and isolated modes. It persists the isolation snapshot and only touches items whose visibility changes. Addresses R-S3, R-S10 and R-B10.
4. **Menu commands through `FocusedValue`** instead of NotificationCenter, with a single main window. Addresses R-S14 and R-B1.
5. **Smaller views.** Move sorting, filtering and search into a navigator view model that publishes rows. Make the editor draft-based and keyed by item (R-S1). Use one color table (R-S21).

Do these after the upstream rebase (R-E2), because upstream changed the CoreApi place-page files and `UserLineMark::IsVisible()`, which the visibility work depends on.
